# Report notes: Autonomous CV-Based Human-Following Robot

This is ready-to-use material for the mini-project write-up. Everything here
describes what is **actually implemented** in this repository. Every number
comes from `tools/benchmark.py` and `tools/evaluate_synthetic.py`.

> Before you submit, re-run `python tools/benchmark.py` on the laptop you use for

## 1. Problem statement

Design and implement a system that lets a mobile robot **autonomously follow a
human using a single monocular RGB camera**. In real time, the system must
detect people, select and keep one target person, estimate the target's
horizontal position and approximate distance, and produce motion commands
(FORWARD, BACKWARD, LEFT, RIGHT, LEFT+FORWARD, RIGHT+FORWARD, STOP). The
commands must be stable, not jittery, and the robot must stop safely whenever
the target is lost or uncertain. Because no physical robot is available, the
commands drive a 2-D kinematic robot simulator.

## 2. Dataset details

* **We did not train a model.** Person detection uses publicly released
  pretrained weights:
  * **YOLOv8n** (Ultralytics), trained on **MS-COCO 2017**: about 118k training
    images, 80 object classes, including *person*.
  * **SSDLite320-MobileNetV3-Large** (torchvision), also trained on MS-COCO
    2017. This is the same detector family (MobileNet + SSD) as the reference
    paper's TensorFlow MobileNet-SSD.
  * We use only the COCO class `person`.
* **Unsupervised components** (K-Means, Felzenszwalb) need no labelled data.
  K-Means is fitted on each analysed frame at run time.
* **Test data:**
  1. **Live webcam** during the demo (qualitative).
  2. A **synthetic test video** with ground truth (`data/samples/test_walk.mp4`,
     440 frames, 640×480, 20 fps), generated by `tools/make_test_video.py`. Two
     real pedestrian crops (from the sample image `bus.jpg` bundled with
     Ultralytics) are pasted onto a drawn indoor scene and moved along a scripted
     path in 7 phases: far and centred → far and left → ideal and right → ideal
     and centred → too close → disappears for 25 frames → re-appears while a
     second person walks across. The exact boxes of the target and the
     distractor are saved per frame (`test_walk_gt.csv`).
* **Optional custom data:** `data/collect_data.py` captures webcam frames, with
  optional YOLO-format pseudo-labels from the detector. These must be checked by
  hand before use as ground truth.

## 3. Approach

The design is adapted from the reference paper (Gupta & Gloria, *Golf Bag
Carrier Robot Computer Vision*). That paper used a camera-only pipeline: a
pretrained MobileNet-SSD for golfer detection and tracking, plus K-Means,
Felzenszwalb and convolution + softmax for terrain classification. Our pipeline is:

```
Webcam → CNN person detector → target selection → Kalman tracking
      → position (LEFT/CENTER/RIGHT) + distance proxy (FAR/IDEAL/CLOSE)
      → [optional K-Means / Felzenszwalb terrain cue]
      → rule-based decision engine + temporal smoothing → robot command → simulator / UI
```

**Key design decisions**

1. **Pretrained single-stage CNN detector (YOLOv8n).** It is accurate and runs
   in real time on a CPU. The paper's MobileNet-SSD family is offered as an
   alternative so the two can be compared.
2. **Track, don't just detect.** A constant-velocity Kalman filter (as in SORT)
   smooths boxes and predicts through short misses. Gated association (IoU or
   bounded centre jump) stops the robot from switching to another person. A
   colour-histogram appearance model re-identifies the target after a loss.
3. **Monocular distance proxy.** We use box height divided by frame height
   (pinhole model: size ∝ 1/distance), mapped to FAR/IDEAL/CLOSE with four
   thresholds that form hysteresis bands. We do **not** claim metric depth. A
   rough metric estimate is shown only as "approx." with its assumptions stated.
4. **Explainable, safety-first decision engine.** It uses a priority rule table.
   A lost target or low confidence gives an immediate STOP.
5. **Three-layer temporal smoothing.** EMA, hysteresis and a command debouncer
   (persistence frames + minimum command duration) remove jitter. Safety STOP
   bypasses the debouncer.
6. **Terrain analysis as an experimental cue.** This follows the paper's K-Means
   colour filter and Felzenszwalb + pooling. It labels as ground any segment
   covering the patch directly in front of the robot, plus any segment of
   similar colour, and computes the free-space depth per corridor. It only
   affects motion with `--terrain-veto`.

## 4. Implementation

* **Language and libraries:** Python 3; OpenCV (I/O, K-Means, drawing);
  NumPy; Ultralytics (YOLOv8n); PyTorch/torchvision (SSDLite); scikit-image
  (Felzenszwalb, optional).
* **Modules:**

| Module | File | Input → Output |
|---|---|---|
| Detector | `detection/person_detector.py` | frame → person boxes + confidences |
| Target selector | `detection/target_selector.py` | detections + prediction → chosen detection |
| Tracker | `tracking/tracker.py`, `tracking/kalman.py` | frame + detections → smoothed box, state (TRACKING/COASTING/LOST) |
| Position estimator | `navigation/position_estimator.py` | box → error_x, LEFT/CENTER/RIGHT, bearing |
| Distance estimator | `navigation/distance_estimator.py` | box → height ratio, FAR/IDEAL/CLOSE |
| Decision engine | `navigation/decision_engine.py` | position, distance, confidence, visibility → command |
| Smoothing | `utils/smoothing.py` | noisy values/commands → stable values/commands |
| K-Means / Felzenszwalb | `segmentation/*.py` | frame → segments, traversable mask, path-blocked flag |
| Simulator | `simulation/robot_simulator.py` | command, dt → robot pose, top-view image |
| Dashboard | `visualization/dashboard.py` | frame state → annotated window |
| Pipeline | `pipeline.py` | frame → full `FrameState` (shared by demo, tests and benchmark) |

* **Main parameters** (`config.py`): `CONFIDENCE_THRESHOLD = 0.45`,
  `HORIZONTAL_THRESHOLD = 0.18` (normalised), `HORIZONTAL_HYSTERESIS = 0.06`,
  distance thresholds `0.50 / 0.55 / 0.80 / 0.90` (box height ÷ frame height),
  `SMOOTHING_FACTOR = 0.4`, `COMMAND_PERSISTENCE_FRAMES = 4`,
  `MIN_COMMAND_DURATION = 0.4 s`, `LOST_TIMEOUT_FRAMES = 15`, `KMEANS_K = 4`,
  YOLO input size 320.
* **Safety behaviour:** STOP when the camera fails, the model fails, the target
  disappears, confidence is low, or the tracker becomes invalid; on pause, on
  quit and on Ctrl+C. If one detector fails to load, the other is tried. Missing
  packages, a bad camera index and missing files produce clear error messages
  instead of crashes.
* **Testing:** 36 automated tests (`python -m unittest discover -s tests`)
  cover position and distance classification including hysteresis, the
  debouncer, the full decision rule table and safety stops, simulator
  kinematics, target selection (single person, several people, gating), tracker
  state transitions, rejection of invalid boxes, K-Means and Felzenszwalb
  path-blocked detection on synthetic scenes, and an end-to-end run with the real
  detector on the sample video.

## 5. Results (measured)

**Synthetic test video, YOLOv8n, default settings** (`main.py --source data/samples/test_walk.mp4 --headless --log` followed by `tools/evaluate_synthetic.py`):

| Metric | Value |
|---|---|
| Frames with the target tracked while it was visible | 415 / 415 (100 %) |
| Mean IoU of the tracked box vs the ground-truth box | 0.942 |
| Identity switches to the distractor person | 0 frames |
| Position label agreement with ground-truth-derived labels | 96.6 % |
| Distance-zone agreement (frames outside hysteresis bands) | 99.2 % |
| Frames where the robot moved while the target was LOST | 0 |
| Behaviour during the 25-frame disappearance | coasting for 15 frames, then LOST + STOP; re-identified on reappearance (colour similarity 0.89) |
| Detector latency (mean / p95) | 26.7 / 34.3 ms |
| Tracker latency (mean) | 0.36 ms |
| End-to-end processing rate (headless) | 36.2 FPS |

**Commands per scenario phase** (dominant command in **bold**):
A far + centre → **FORWARD** (57/60); B far + moving left → **LEFT+FORWARD** (44/60);
C approaching ideal and moving right → LEFT+FORWARD → FORWARD → **RIGHT**;
D ideal + centre → RIGHT, then **STOP** (35/60); E growing until too close → STOP, then **BACKWARD** once past the CLOSE threshold (25/50);
F target gone → **STOP**; G re-acquired, far and slightly left → **LEFT+FORWARD**.

**Comparison and ablation** (`tools/benchmark.py`):

| Configuration | FPS (processing) | Detector ms | Mean IoU | Command changes |
|---|---|---|---|---|
| YOLOv8n, every frame | 36.0 | 26.9 | 0.942 | 9 |
| YOLOv8n, every 3rd frame + Kalman prediction | 94.5 | 26.5 | 0.907 | 9 |
| MobileNetV3-SSDLite (paper's detector family) | 14.2 | 69.4 | 0.896 | 9 |
| + K-Means segmentation (every 5th frame) | 36.8 | seg 5.0 ms | 0.942 | 9 |
| + Felzenszwalb segmentation (every 15th frame) | 38.5 | seg 7.1 ms | 0.942 | 9 |
| ±12 px box jitter, smoothing ON | 37.6 | 25.7 | 0.804 | **9** |
| ±12 px box jitter, smoothing OFF | 38.3 | 25.3 | 0.804 | **32** |

**Observations**

* YOLOv8n was about 2.6× faster than MobileNetV3-SSDLite on this CPU and
  produced tighter boxes (IoU 0.94 vs 0.90).
* Running the detector every 3rd frame and bridging the gaps with Kalman
  prediction raised throughput about 2.6× with only a small IoU loss. On a slow
  laptop, use `--detect-interval 2` or `3`.
* OpenCV's MIL tracker took about 50 ms per update, slower than YOLOv8n, so
  it is not used by default.
* Without temporal smoothing, box jitter caused 3.6× more command changes (32
  vs 9). Smoothing costs a little responsiveness: position agreement at phase
  transitions is slightly lower because of the deliberate lag.
* *Live-webcam observations:* record your own here (for example FPS on your
  laptop, and behaviour with 2–3 people or in dim light). Do not report numbers
  you did not measure.

**Limitation of these results:** the test video is synthetic, so it validates
the software pipeline and the decision logic. It does not measure detection
accuracy in the wild. The quoted COCO accuracy of the pretrained models belongs
to their authors (Ultralytics / torchvision documentation), not to us.

## 6. Conclusions

* A pretrained CNN detector combined with lightweight tracking and transparent
  rules is enough to build a real-time, camera-only human follower on an
  ordinary CPU. This confirms the reference paper's finding that an
  off-the-shelf MobileNet-SSD-class detector can track the target person, and
  shows that a newer single-stage detector (YOLOv8n) is faster and more precise
  for the same job.
* **Tracking and target selection matter as much as detection.** Gated
  association and re-identification kept the correct person through occlusion
  and a crossing distractor.
* **Temporal smoothing is essential** for usable robot commands. It cut command
  switching by about 3.6× under jitter.
* **A monocular box-height proxy is sufficient for FAR/IDEAL/CLOSE following**,
  but it is not metric depth. Calibration (key `c`) adapts it to the room.
* **Unsupervised colour segmentation (K-Means, Felzenszwalb) gives only a weak,
  experimental terrain cue**, which matches the paper's conclusion that terrain
  classification is the harder problem. A supervised classifier (the paper's
  convolution + softmax) or a depth sensor would be needed for reliable obstacle
  avoidance.
* **Future work:** connect the commands to real motors (e.g. an ESP32 over
  serial), use proportional velocity control, learned re-ID features
  (DeepSORT/ByteTrack), monocular depth networks, and fine-tuning on footage from
  the robot's own camera.

## 7. Viva quick answers

* **Where is the ML?** The CNN detector (YOLOv8n / MobileNet-SSD, supervised and
  pretrained on COCO) and K-Means (unsupervised). The Kalman filter is a
  probabilistic estimator.
* **Did you train it?** No. We used transfer of a pretrained model as-is. We
  state this explicitly, and training on our own data is future work.
* **Why not just detection?** Detection is noisy and sometimes misses, and it
  has no identity. The tracker adds temporal consistency, prediction and
  identity.
* **How do you know the distance?** We don't, metrically. Box height is a
  relative proxy (pinhole model), with thresholds and hysteresis.
* **What if the person leaves?** COASTING for up to 15 frames, with the
  confidence decaying; the command becomes STOP once it falls below the
  threshold. After that the target is LOST and the robot STOPs. On reappearance
  the target is re-identified by appearance.
* **Why does the robot turn LEFT when I step right?** The camera faces you.
  Your right is the robot's left. Frames are not mirrored.
